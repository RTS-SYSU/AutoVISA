2026 年 11 月 11 日。此工作包接通本地 Web 的反馈纵向流程，使用已有 W04 运行、路线版本和 W03 来源绑定生成可核对提案。

## 使用

在项目根目录执行：

~~~powershell
.\start-workbench.ps1 -W04Demo
~~~

打开 http://127.0.0.1:8765/reasoning?run=90ca931fa03f403a8d58b4abe86b4996 。演示使用独立验收目录。正式工作台仍从已经检查的映射进入双向推导。

1. 点击节点中的“对这个节点提出反馈”，或对齐卡片的“对此对齐反馈”；也可在表单选择具体节点、对齐或推导关系。
2. 填写意见与作者，选择“从反馈识别”或明确的处理方式。示例按钮只填入内容，提交由用户执行。
3. 点击“形成修订提案”，查看解释、修改前后陈述、候选路线与所选路线涉及的目标、证据处理和待检查命题。
4. 从“本运行的已保存提案”重开历史记录。页面地址保留当前提案，刷新后恢复。路线后续改变时，旧提案标明基于历史路线，并保留原影响结果。

## 本轮支持的具体处理

| 意见 | 提案结果 | 检查与影响 |
|---|---|---|
| 拆分 response_bridge 调度桥接义务 | 新增服务下界、服务上界，两者共同支持原义务；列出候选路线变化 | 保留原全称量词、所有模型前提和截止端点；结构与 IR 类型检查通过；两条义务及联合充分性均等待证明 |
| 核对最小释放间隔 | 记录 legal_arrivals 的定义、来源和使用该条件的义务 | 原模型已有条件，不重复添加假设；说明对齐与调度桥接各自使用的前提 |
| 核对对齐方向与实例化 | 保存原有方向、变量替换、条件及回执的核对记录 | 数学关系保持不变 |
| 反转对齐 | 明确交换支持与义务，列出反向蕴含及重新建立实例化的任务 | 不沿用原方向的证明；登记关键数学确认要求 |
| 修改时间域或模型范围 | 保存原范围与修改请求原文 | 标为待明确形式化，列出上下文变化可能涉及的目标与证据 |
| 含糊、多方向或无法处理的意见 | 保存原反馈和待补充项 | 不虚构具体修改或证明完成状态 |

处理器明确标为 **local_rules**。自动识别是小范围的词句规则，支持显式处理方式选择；它不是通用自然语言数学推理。所有结果展示处理依据和实际执行的动作。本轮没有调用外部模型 API。

## 拆分的数学含义

对原桥接义务中的任意任务集、合法到达和有效调度，原结论要求每个作业在截止点前获得恰好等于需求量的服务。提案分别要求：

- 需求量 ≤ 从释放时刻到截止时刻前的服务量。
- 同一服务量 ≤ 需求量。

两个新陈述保留原义务的外层全称量词、全部前提、作业与任务对应条件，以及区间 [release, release + D)。提案还显式保存“下界义务 → 上界义务 → 原桥接义务”的精确充分性待证命题。

原桥接节点保留，新义务与连接只存在于独立提案预览中。结构和 IR 类型通过不代表 Rocq 已证明；proof 字段为 not_run。主要目标仍未证明。

## 数据与模块边界

FeedbackWorkspace 提供 submit、read、history。HTTP、界面和验收调用同一业务接口。模块复用既有来源、映射、图验证、命题类型与内容存储，没有新增模型提供方或证明检查抽象层。

每份提案保存：

- 原始反馈文本（包含换行和首尾空格）、作者、对象种类与稳定身份。
- 原运行、所见路线版本、映射、冻结上下文和语义修订。
- 原对象、原图、路线和 IR 的内容摘要，以及实际生成器源码。
- 具体 before/after、后续检查任务、来源片段与精确定位。
- 全部候选路线的下游影响，以及提交时所选路线的下游影响。
- 相关原证据及采用后需要重新检查的关系。

derivation_feedback 与 revision_proposals 仅追加；一条反馈与其提案在同一数据库事务中登记。工作台在返回提交成功前发布数据库备份。历史读取验证已有内容，不按新版本规则重新生成旧提案。批量历史读取只核对一次共享原运行和映射，避免每份提案重复读取整套证明产物。

W05-a 没有采用提案操作；adopted 恒为 false。原图、目标修订、证明尝试和历史回执保持原样。关键数学确认在提案中登记，真正的确认与采用属于 W05-b。
